## 2. RALPLAN-DR 의사결정 요약

### 원칙 (Principles)
1. **사용자 체감 가치 우선** — 응답 정확도·속도·맥락 유지가 화려한 기능보다 먼저.
2. **측정 없이는 개선 없다** — 평가 하니스를 품질 작업의 전제조건으로 둔다.
3. **부채 먼저, 기능 나중** — 구식 의존성 위에 기능을 쌓으면 비용이 복리로 증가.
4. **안전은 협상 불가** — 반려동물 건강 관련 도메인은 면책·범위제한 필수.
5. **작은 단위로, 되돌릴 수 있게** — 각 항목은 독립 배포·롤백 가능하게.

### 핵심 의사결정 동인 (Top 3 Decision Drivers)
1. **노력 대비 효과(ROI)** — 학생/팀 프로젝트로 리소스 한정.
2. **리스크** — 안전(건강 오정보)·보안(`allow_dangerous_deserialization`)·회귀.
3. **확장 기반** — 이후 기능을 떠받칠 측정·설정·테스트 토대.

### 검토된 우선순위 옵션 (Viable Options)
- **옵션 A — 기능 우선(멀티모달/음성부터)**: 데모 임팩트 큼. ✗ 그러나 맥락·평가 토대 없이 쌓으면 회귀 통제 불가, 부채 확대. → **기각**.
- **옵션 B — 부채/기반 우선(채택)**: 캐싱·메모리·의존성·평가부터. 단기 데모 효과는 낮으나 이후 모든 작업의 단위비용을 낮춤. → **채택**.
- **옵션 C — 풀 파인튜닝/자체 LLM 전환**: QLoRA Mistral 활성화. ✗ 회고록에서 이미 "시간 대비 성능 미달" 확인, 비용·운영 부담 큼. → **보류(연구 트랙으로 분리)**.

**채택 근거**: 원칙 2·3에 따라, 평가와 기반 정비 없이 진행하는 기능 확장은 측정 불가능한 리스크를 키운다. 옵션 B는 ROI·리스크·확장기반 3개 동인 모두에서 우위.

## 3. 단계별 로드맵 (제안)

### T1 — 기반·정합성 (저위험 / 고가치) ⭐ 최우선 — ✅ 구현 완료 (2026-06-08, 런타임 검증 대기)
| ID | 작업 | 해결 약점 | 상태 | 구현 위치 |
|----|------|-----------|------|----------------|
| T1-1 | 임베딩+FAISS+LLM 로드를 `@st.cache_resource`로 래핑 (+ 유휴 시 RAM 해제용 TTL) | W3 | ✅ | `app.py` `get_resources()`, `QA_bot.py` `build_resources()` |
| T1-2 | **대화 메모리 도입** (history-aware 질문 재작성 + 세션 히스토리 전달) | W1 | ✅ | `QA_bot.py` `contextualize_question()`/`to_lc_history()`, `app.py` |
| T1-3 | LangChain import 마이그레이션(`langchain.*` → `langchain_community.*`/`langchain_core.*`) | W2 | ✅ | `QA_bot.py:1-9` (후속: `langchain-openai`/`-huggingface`) |
| T1-4 | 번역 경로 단일화(영어 출처일 때만 추가 검색, 답변 생성 1회) | W4 | ✅ | `QA_bot.py` `adaptive_retrieve()`/`answer_stream()` |
| T1-5 | 스트리밍 응답(커스텀 말풍선 유지) | W5 | ✅ | `app.py` `st.empty()` + `answer_chain.stream()` |

> **운영 메모 — 리소스 캐시 TTL (NAS)**: bge-m3 가중치 + FAISS 인덱스는 한 번 로드되면 프로세스가 살아있는 동안 RAM에 **상시 상주**(~2–4GB baseline). NAS RAM이 빠듯한 환경을 위해 `@st.cache_resource(ttl=...)`로 **유휴 시 메모리 해제**를 선택할 수 있게 한다. 기본값 `1h`(마지막 사용 후 1시간 유휴 시 해제), 환경변수 `RESOURCE_CACHE_TTL`로 조정. `none`/`0`/빈값 → 만료 없이 영구 상주(반응성 우선). 트레이드오프: TTL 만료 후 첫 질문은 2GB 재로딩으로 콜드스타트 지연 발생.

> **트레이드오프(실제 긴장)**: T1-3(의존성 마이그레이션)과 T1-2(메모리)는 같은 파일을 건드린다. **마이그레이션을 먼저** 하면 메모리 구현을 신 API(`create_retrieval_chain`) 위에 한 번에 작성 → 재작업 회피. 단, 마이그레이션은 회귀 위험이 있으므로 **T0로 평가 하니스(T2-2)의 최소판을 먼저 깔고** 진행하는 것을 권장(아래 시퀀싱 참조).

### T2 — RAG 품질 — ✅ 구현 완료 (2026-06-08, 런타임/품질 검증 대기)
| ID | 작업 | 상태 | 구현 위치 |
|----|------|------|-----------|
| T2-1 | 검색 고도화: 하이브리드(BM25+dense Ensemble) + 리랭커(`bge-reranker-v2-m3`) | ✅ | `QA_bot.py` `_build_retriever()` — `USE_HYBRID`/`USE_RERANKER` 토글, 부재 시 dense 폴백 |
| T2-2 | **자동 평가 하니스**(ragas: faithfulness/answer-relevancy/context-precision), TC01~05 | ✅ | `scripts/eval_ragas.py`, `data/eval/testcases.json` (사용자 실행) |
| T2-3 | 범위 외 가드레일(LLM 분류) + 건강 면책 고지(키워드) | ✅ | `QA_bot.py` `is_in_scope()`/`needs_health_disclaimer()`, `ENABLE_OOS_GUARD` |
| T2-4 | 출처 렌더링 개선: 중복 제거 + 제목 기반 클릭 링크 | ✅ | `app.py` `build_sources()`/`render_sources()` |

> **T2-1 운영 주의(NAS)**: 리랭커 `bge-reranker-v2-m3`는 추가 **~2.3GB 모델 다운로드 + 상시 RAM**을 요구한다(bge-m3와 별개). NAS RAM이 빠듯하면 `USE_RERANKER=0`(하이브리드만) 또는 `USE_HYBRID=0 USE_RERANKER=0`(dense-only)로 단계적 비활성화 가능. 모델/`rank_bm25` 부재 시 자동으로 dense로 폴백한다.
> **검증 한계**: BM25/Ensemble 배선과 가드레일·출처 로직은 정적 검증 완료. 리랭커 모델 로딩·검색 품질·ragas 점수는 모델 캐시가 있는 실제 환경에서 측정 필요 → **T2-2 하니스로 before/after 품질 회귀를 반드시 확인**할 것.

## 4. 권장 실행 시퀀스 (의존성 고려)

```
1주차: T2-2(평가 최소판) → T1-3(의존성 마이그레이션) → T1-1(캐싱) → T1-5(스트리밍)
2주차: T1-2(대화 메모리) → T1-4(번역 단일화) → T2-3(가드레일/면책) → T2-4(출처)
3주차: T4-2(설정) → T4-1(테스트/CI) → T4-3(보안) → T4-4(자산 정리)
이후 : T2-1(검색 고도화) → T3-1(피드백) → T3-2(견종 필터) → T3-3/T3-4(멀티모달·음성)
```

**핵심 인사이트**: 평가 하니스(T2-2)를 의도적으로 **맨 앞**에 둔다. 마이그레이션·메모리·검색 변경의 품질 효과를 수치로 검증해야 회귀 없이 전진할 수 있다(원칙 2).

## 5. ADR (Architecture Decision Record)

- **결정**: 기능 확장에 앞서 "평가 하니스 → 의존성/기반 정비 → 대화 품질" 순의 부채 우선 로드맵을 채택한다.
- **동인**: 한정된 리소스(ROI), 안전·보안·회귀 리스크, 후속 작업의 확장 기반 필요.
- **검토 대안**:
  - A) 기능(멀티모달/음성) 우선 — 데모 임팩트는 크나 측정·맥락 토대 없이 회귀 통제 불가로 기각.
  - C) 자체 LLM 파인튜닝 전환 — 회고에서 효과 미달 확인, 연구 트랙으로 보류.
- **선택 이유**: 옵션 B가 3대 동인(ROI/리스크/확장기반) 모두에서 우위. 평가를 전제조건화해 이후 모든 변경을 측정 가능하게 만든다.
- **결과(Consequences)**:
  - (+) 변경 단위비용 하락, 회귀 가시화, 안전 리스크 완화.
  - (−) 1~2주차 동안 가시적 신기능이 적어 데모 임팩트는 지연됨 → 이해관계자에게 "토대 투자" 프레이밍 필요.
- **후속(Follow-ups)**: T2-2 평가 지표 기준선 측정 → 각 변경의 before/after 기록 → T3 진입 전 품질 게이트 통과 확인.

## 6. 검증 기준 (Acceptance, 측정 가능)

- **T1-2 대화 메모리**: "말티즈가 짖어요" → "그럼 어떻게 훈련해?" 후속 질문에서 직전 견종/맥락을 유지해 응답. (수기 + ragas 대화셋)
- **T1-3 마이그레이션**: 앱 정상 기동 + TC01~05 ragas 점수가 기준선 대비 **하락 없음**.
- **T1-4 번역 단일화**: 영어 출처 질의의 LLM 호출 횟수 2→1, 평균 응답시간 측정상 감소.
- **T2-2 평가 하니스**: `pytest`(또는 스크립트)로 TC01~05 자동 실행, faithfulness/context-precision 점수 리포트 산출.
- **T2-3 가드레일**: 범위 외 입력(페럿 등)에 "미지원 안내 + 일반 가이드", 건강 질의에 면책 고지 노출.
